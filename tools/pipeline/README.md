# 闭环审查流水线

四个角色轮流上场，每一轮都是一次完整闭环，直到裁判判定"干净"：

```
  ┌──────────┐   findings.json   ┌────────┐   补丁 + 编译   ┌────────┐   实测输出   ┌───────┐
  │ 审查者   │ ────────────────▶ │ 修复者 │ ──────────────▶ │ 测试者 │ ───────────▶ │ 裁判  │
  │ reviewer │                   │ fixer  │                 │ tester │              │ judge │
  └──────────┘                   └────────┘                 └────────┘              └───────┘
        ▲                                                                              │
        │                         score < 9.0 或未 accept                               │
        └──────────────────────────────────────────────────────────────────────────────┘
                                   score ≥ 9.0 且 accept → 干净，停止
```

四个角色是**四次独立的 agent 调用**，各自只有自己的上下文。它们之间唯一的通信方式是磁盘上的产物文件，
所以每个人写的 JSON 都必须自解释——不依赖"上一轮我们说过什么"。

## 为什么必须分开

| 角色 | 唯一职责 | 明确禁止 |
|---|---|---|
| 审查者 | 指出缺陷，附证据 | 改任何源码 |
| 修复者 | 按清单出补丁，编译通过 | 自己跑 GUI 回归、自己提交 git |
| 测试者 | 真跑，报原始输出 | 改 `src/` 下任何文件 |
| 裁判 | 独立复核 + 打分 | 改代码、改别人写的报告 |

分开的理由不是为了好看：**同一个人既找 Bug 又判自己修好没有，一定会给自己打分**。
流水线把"提问题""改问题""证明改对了""判定能不能收工"拆成四个互不信任的环节，
每一步都能被下一步用机械证据推翻。

```
│   ├─ fixer.md

../_pipeline/                 运行产出，不进 git（和 _build 一个待遇）

└─ round-NN/

```

## 判定"干净"的四个条件

全部满足才算，缺一条就再来一轮：

1. 本轮 `Critical + Major` 未解决数 = 0（`fix.json` 里状态必须是 `fixed` 或有裁判认可的 `wontfix` 理由）
2. 构建 0 error，测试者指定的全部回归套件 `rc=0`
3. 测试者报告的 `regressions` 为空（没有把原来能用的搞坏）
4. 裁判 `score ≥ 9.0` 且 `accept = true`

`gate.py` 把前三条做成机械判定，第四条只认 `verdict.json` 里的数字。
人（编排者）不参与判断，只负责派活和按闸门结果提交或回滚。

## 评分表（裁判用，写进 judge.md）

| 维度 | 权重 | 看什么 |
|---|---|---|
| 缺陷真实性 | 25% | 报的问题真的存在吗？证据能复现吗？有没有把设计当 Bug |
| 修复正确性 | 30% | 根治还是打补丁？边界还漏吗？有没有引入新问题 |
| 测试证据 | 25% | 真跑了还是声称跑了？断言能失败吗（反向验证）|
| 覆盖广度 | 10% | 还有多少区域本轮没碰 |
| 工程规范 | 10% | 改动最小化、注释、提交粒度 |

锚点：`10` 无 C/M 且有实测证据；`8–9` 只剩 Minor/Info；`6–7` 还有 Major 未修；`<6` 有 Critical 或存在回归。

## 轮次纪律

- 单轮只允许修 `findings.json` 里列出的条目，**不许顺手重构**（顺手改的东西没有审查记录，等于绕过流程）。
- 每轮结束由编排者提交一笔 git，message 带轮次与 finding 编号；裁判 `accept=false` 的轮次**不提交**，先回滚再进下一轮。
- 轮次上限 `MAX_ROUNDS = 5`。到上限仍未干净，如实记录"未收敛"，不伪造通过。
- 每轮 `brief.md` 必须写明：本轮范围、上轮未解决项、**已知非缺陷排除清单**（防止反复报同一批误报）。

## 手动跑一轮

```bat
rem 1. 写本轮任务书
rem    _pipeline\round-01\brief.md

rem 2. 派四个 agent（编排者做，不是脚本做）
rem    reviewer -> fixer -> tester -> judge

rem 3. 机械判定
python tools\pipeline\gate.py _pipeline\round-01

rem 4. 看退出码
rem    0 = 干净，停             1 = 继续下一轮            2 = 打回，回滚修复
```

`gate.py` 退出码约定见脚本头部注释。它不联网、不调模型，只读 JSON 做算术。
