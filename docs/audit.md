## 转职／觉醒编码与 PVF 职业名称（2026-11-19）

原 ELF 的访问器将 `grow_type` 分为低四位转职分支、4..6 位觉醒阶段；第 7 位独立，
原设置函数会保留它。例如 17 为分支 1／一觉，33 为分支 1／二觉。旧界面将字节直接当成
觉醒次数，无法回填这些值，只改职业也可能将它归零。现在下拉框使用实际字节，换职业
保留完整原值，改转职／觉醒保留第 7 位；未知值作为当前选项保留。

原库的 `grow_type` 是有符号 TINYINT，直接写 145 会被非严格 MySQL 截为 127。
GM 内部统一读作原始字节，写入时识别字段类型，有符号字节存储为 -111；严格模式也能
正确往返。职业 ID 的默认名称顺序已修正；PVF 名称改读 `.chr` 的 `[growtype name]`，
不再读取这些文件不存在的 `[name]`。缓存版本同时更新，旧版本重新解析。

Windows Native 与原版 Linux 各完成四轮生产数据入口修改、真实 Robot 登录、原游戏的
原始字节／分支／阶段读取和正常下线保存：2、17、33、145，结果一致。每端三项定向数据
回归覆盖 0／127／128／145／255 等字节边界、严格模式、幂等、归属、删除、在线及上线竞态。
两端的实际 GM 窗口均通过有／无 PVF 的回填、职业切换与高位保留。PVF 的 11 个职业、
66 个分支名称逐项符合原始 token；首次解析、缓存和旧版本重建的 495592 行语义输出一致。
职业修改仍要求离线，本阶段没有增加在线转职或修改原版指令。

环境沿用原 i386 game `da417c5e…b79979`、PVF `c3dde22a…22dec`、MySQL 5.7.44、
Windows 10 x64 build 19044／Native x86，与已授权的 Ubuntu 22.04.5／WSL2 Linux
5.10.16.3 比较副本。上述结果限于已测字节的原函数和存档，不代替图形客户端技能验收。

**更正历史编码判断**：已验证的原 ELF 使用 latin1 会话传递 UTF-8 名称字节，
utf8 列中表现为 Windows-1252 包装。直接按普通 UTF-8 SQL 值改名，虽然 SQL 客户端
显示正常，游戏读取时仍可能变为问号。因此不能沿用下文“禁止二次转码”的历史结论。

发件人时使用局部 SQL 值转换，保持连接字符集和原始备份字节语义；不批量改写数据库。
名字搜索兼容两种存储；克隆同步到 charac_view 的名称使用实际游戏字节。
字段长度按原 ELF 字节容量校验，拒绝截断成功。

PVF 的另一处根因是把 stringtable 的二进制偏移区用于码页判断，并误将部分文本
继续当作索引。现在按 count+1 个偏移读取 count 个字符串，从整表采样完整文本条目，
统一选择 UTF-8、GBK 或 Big5；n_string 文本也识别编码。缓存版本 PVFC8 升至 PVFC9，
旧缓存自动重建。实测 stock PVF 为 Big5，83,454 个物品，编号 1 为“復活幣”；
用户指定的客户端 PVF 为 GBK，116,433 个物品，编号 1 为“复活币”。保留 PVF 自身用字。

PVF 表 N-2（一级为零）。改等级在一个事务内同步 charac_info.exp、charac_stat.exp；
缺失 PVF、曲线重置或超出有符号字段时明确拒绝。两端 50/60/70 级登录、移动、退出、
