## 原 ELF 联调与中文修复（2026-11-18）

以下为最新实测；后文 2026-11-12 的结论、产物及边界保留为历史记录。
本轮在独立副本中使用相同原版 `df_game_r`（SHA-256
`da417c5e65918f655afcddb6edfdaf2fa1e77b2f208e5aa397f021fa23b79979`）、
stock PVF、MySQL 5.7.44 及 DP2/Frida，对照 Windows Native 和 Linux 原 ELF。
Windows 为 Windows 10 IoT Enterprise LTSC 2021 x64 build 19044，GM 为 Zig 构建的
Windows x64 程序；Linux 对照运行于已授权的 WSL2 5.10.16.3/Ubuntu 22.04.5，
原 ELF 使用私有 glibc 2.17 环境。GM 在 Windows 上连接两端 MySQL，不是 Linux GUI。
这不等于裸机 Linux 或其他服务端版本的验收。

**更正历史编码判断**：已验证的原 ELF 使用 latin1 会话传递 UTF-8 名称字节，
utf8 列中表现为 Windows-1252 包装。直接按普通 UTF-8 SQL 值改名，虽然 SQL 客户端
显示正常，游戏读取时仍可能变为问号。因此不能沿用下文“禁止二次转码”的历史结论。
GM 对已确认的角色名、宠物名、活动说明等展示字段做可逆恢复；仅在完全可逆且恢复
结果为有效 UTF-8 时转换，普通 UTF-8 保持原值。写入角色名、宠物名、邮件正文及
发件人时使用局部 SQL 值转换，保持连接字符集和原始备份字节语义；不批量改写数据库。
名字搜索兼容两种存储；克隆同步到 charac_view 的名称使用实际游戏字节。
字段长度按原 ELF 字节容量校验，拒绝截断成功。

PVF 的另一处根因是把 stringtable 的二进制偏移区用于码页判断，并误将部分文本
继续当作索引。现在按 count+1 个偏移读取 count 个字符串，从整表采样完整文本条目，
统一选择 UTF-8、GBK 或 Big5；n_string 文本也识别编码。缓存版本 PVFC8 升至 PVFC9，
旧缓存自动重建。实测 stock PVF 为 Big5，83,454 个物品，编号 1 为“復活幣”；
用户指定的客户端 PVF 为 GBK，116,433 个物品，编号 1 为“复活币”。保留 PVF 自身用字。

等级经验也更正了历史的 exp=0 假设：原 ELF 使用累计经验，等级 N 的下限取
PVF 表 N-2（一级为零）。改等级在一个事务内同步 charac_info.exp、charac_stat.exp；
缺失 PVF、曲线重置或超出有符号字段时明确拒绝。两端 50/60/70 级登录、移动、退出、
重登后的等级和经验已对照；金币、复活币、SP/TP/QP、点券、材料槽和材料附件也完成
两端实际协议会话及存档检查。此项不是全客户端页面人工验收。

在线 coin 被退出存档覆盖已在 Linux 原 ELF 实际复现：内存 17、SQL 改成 40，退出后
SQL 回到 17。现在角色数值、容器和宠物等写入在后台执行时重新核对原始登录状态，
避免仅依赖 GUI 缓存或通道总人数；查询失败或账号仍在线则拒绝写入。
这不提供在线即时 GM 接口；泡点在线复活币路径仍需后续修复，不能将本次防护写成
全部在线业务已解决。

本轮证据保留于仓库外 `../x/dnf-gm-output/evidence/`，账号数据与日志不提交：

- Windows 数据层 39 项通过；随后中文克隆槽位、源槽选择与角色备份恢复 3 项通过。
- Windows 中文改名、邮件、宠物、拒绝 emoji、失败回填 5 项通过；中文 PVF 查询和
  发放队列、中文名搜索、原 ELF 会话读取邮件正文等界面路径通过，并逐页截图检查。
  Linux 数据库对应 5 项中文界面用例全部通过。

  存档→SQL 字节比对→恢复原名字，均通过。邮件正文目前验证原 ELF 会话读取字节，
  不能据此声称本次已在客户端阅读中文邮件、宠物名或活动页。
- 最终严格构建、自检通过；人工设置旧 PVFC8 标记的独立缓存被自动重建为 PVFC9，

## 结论与范围

C 项目的 Win32 界面、串行数据库作业、独立物品模型和严格编译适合当前单机 GM 工具。
不需要为“优雅”整体换框架，也不能用代码更少或 exe 更小证明功能更正确。
本轮优先修复可能造成半写入、错误备份、不可见角色和协议异常的问题，并合并重复实现。

对照源：

- [原版 SQL 与物品实现](../../DNF_pvf_python/dnfpkgtool/sqlManager2.py)。

检查了 C 的数据层、MySQL 协议、物品编码、备份还原、后台作业，以及编码、
zlib、PVF/NPK 解析的关键路径；现有回归覆盖界面、队列、连接生命周期和主要写入。
没有把所有分支、所有服务器版本或全部 Python 功能标成已验证。

| 文本/附件邮件 | 正文、时装/宠物、postal 分步提交；按时间查询附件 ID | C 整个发放队列共用事务，使用 LAST_INSERT_ID；按真实 PVF 元数据识别时装/宠物，逐件建立独立附件 |
| 删除邮件 | 附件清除异常被忽略，继续标记邮件删除 | 本轮改为统一事务；校验附件角色归属、物品 ID；批量删除使用 JOIN，避免逐邮件查询 |
| 克隆角色 | 两参考功能范围不同，不能据此认定完整等价 | C 按表结构发现角色表并重映射主键；本轮校验并同步角色列表槽，失败回滚 |
| 角色备份 | 老唐版 SQL/压缩备份，支持选择表与目标账号 | C 使用角色表发现 + 账号共享表白名单；与老唐选择性恢复/换账号功能不完全等价 |
| 全库备份 | 原版整库 pickle+zlib；老唐 gzip+pickle，并用 SSCursor 分块读取 | C 标准 SQL 更便于人工检查；本轮保证读写错误传播和一致读取；大表读取仍未流式化 |
| 全库还原 | 原版会 SET GLOBAL sql_mode，老唐改独立连接和 SESSION 设置 | C 不改全局模式，本轮补齐成功/失败后的会话设置恢复；DDL/MyISAM 仍无法整体回滚 |
| 泡点 | 原版充值函数偏重现有计费行 | C 独立周期调度；固定收件名单、缺行建账、账号去重、角色逐个发放；邮件复用统一路径，溢出或 SQL 失败整笔回滚 |
| PVF 编辑/技能编辑/服务管理 | Python 提供更多编辑器与配套工具 | C 当前 PVF 为只读；这些是功能范围差异，不能宣称完全替代两套 Python 工具 |

## 后续优化计划与验收标准

2. **补齐已识别的业务差口**：数值框清零交互、未知物品编号的发放策略；

   使用原有 login_status>=1 标志，是否改成仅当前游戏角色及如何识别过期在线位仍需业务确认。
