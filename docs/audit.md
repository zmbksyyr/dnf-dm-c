# 三项目审查与优化记录

审查日期：2026-11-12。目标是校准 `dnf-dm-c` 的实际行为与数据正确性，
并参考两个 Python 项目的业务实现。Python 代码本身也存在缺陷，不能直接当作正确性标准。

## 结论与范围

C 项目的 Win32 界面、串行数据库作业、独立物品模型和严格编译适合当前单机 GM 工具。
不需要为“优雅”整体换框架，也不能用代码更少或 exe 更小证明功能更正确。
本轮优先修复可能造成半写入、错误备份、不可见角色和协议异常的问题，并合并重复实现。

对照源：

- [原版 SQL 与物品实现](../../DNF_pvf_python/dnfpkgtool/sqlManager2.py)。
- [老唐版 SQL 与物品实现](../../老唐GMtool/2026.3.14GMTOOL源码/dnfpkgtool/sqlManager2.py)。
- [老唐版角色备份实现](../../老唐GMtool/2026.3.14GMTOOL源码/dnfpkgtool/charBackupFrame.py)。

检查了 C 的数据层、MySQL 协议、物品编码、备份还原、后台作业，以及编码、
zlib、PVF/NPK 解析的关键路径；现有回归覆盖界面、队列、连接生命周期和主要写入。
没有把所有分支、所有服务器版本或全部 Python 功能标成已验证。

## 功能与 SQL 对照

| 业务 | Python 参考行为 | C 当前行为与判断 |
|---|---|---|
| 61 字节物品槽 | `DnfItemSlot`；装备数量区按大端，其余按小端 | 同布局；与两个参考分别交叉验证 160 个槽的字段与重建字节 |
| 背包 BLOB | 四字节原始前缀 + zlib；修改指定槽 | 保留前缀和未知字节；拒绝非 61 倍数及超限解压，压缩流无需字节相同 |
| 多容器保存 | 通常按调用逐次提交 | 现在外层事务包住本次全部容器；单容器保存加入外层事务 |
| 中文角色名 | 将 UTF-8 字节送入 latin1 会话 | C 按配置字符集发送，避免 utf8 列二次转码；不机械复制参考方式 |
| 等级与经验 | `expTableList` 对应等级阈值 + 1，再更新等级、清处罚，逐步提交 | 界面当前传 exp=0；三步失败可回滚；真实 PVF 经验表已比对，但写入算法仍需游戏校准 |
| 复活币 | `set_pay_coin` 更新 `inventory.pay_coin` | `db_set_coin` 更新读路径使用的 `inventory.coin`；字段语义需按实际服务端确认 |
| 点券/D点 | `cash_cera` 与 `cash_cera_point` 仅 UPDATE | C 的手动设置使用 upsert，支持未生成计费行的账号，并在一个事务内提交 |
| 账号金库/QP | 通常直接 UPDATE | C 对懒建行采用 upsert，已有值不变也可成功，较参考实现完整 |
| 数值清零 | 数据接口可写入 0 | C 部分界面数值框按现有设计拒绝 0；接口支持不代表界面可以操作，需补清零交互 |
| SP/TP/PVP/职业等 | 更新相应业务列 | 主要表与字段对应；输入范围、记录不存在与 SQL 失败由 C 校验；仍需真实服验证显示结果 |
| 文本/附件邮件 | 正文、时装/宠物、postal 分步提交；按时间查询附件 ID | C 整个发放队列共用事务，使用 LAST_INSERT_ID；按真实 PVF 元数据识别时装/宠物，逐件建立独立附件 |
| 删除邮件 | 附件清除异常被忽略，继续标记邮件删除 | 本轮改为统一事务；校验附件角色归属、物品 ID；批量删除使用 JOIN，避免逐邮件查询 |
| 克隆角色 | 两参考功能范围不同，不能据此认定完整等价 | C 按表结构发现角色表并重映射主键；本轮校验并同步角色列表槽，失败回滚 |
| 角色备份 | 老唐版 SQL/压缩备份，支持选择表与目标账号 | C 使用角色表发现 + 账号共享表白名单；与老唐选择性恢复/换账号功能不完全等价 |
| 全库备份 | 原版整库 pickle+zlib；老唐 gzip+pickle，并用 SSCursor 分块读取 | C 标准 SQL 更便于人工检查；本轮保证读写错误传播和一致读取；大表读取仍未流式化 |
| 全库还原 | 原版会 SET GLOBAL sql_mode，老唐改独立连接和 SESSION 设置 | C 不改全局模式，本轮补齐成功/失败后的会话设置恢复；DDL/MyISAM 仍无法整体回滚 |
| 泡点 | 原版充值函数偏重现有计费行 | C 独立周期调度；固定收件名单、缺行建账、账号去重、角色逐个发放；邮件复用统一路径，溢出或 SQL 失败整笔回滚 |
| PVF 编辑/技能编辑/服务管理 | Python 提供更多编辑器与配套工具 | C 当前 PVF 为只读；这些是功能范围差异，不能宣称完全替代两套 Python 工具 |

定位提示：原版 `set_charac_info`、`set_pay_coin`、`send_postal`、
`backup_db`、`restore_db` 分别从 795、850、1022、1190、1234 行开始；
老唐版对应位置为 935、990、1175、1461、1540。

## 本轮已落地

| 问题 | 修复与验证 |
|---|---|
| 内层 START TRANSACTION/COMMIT 提前提交外层工作 | `Db.tx_depth` 合并嵌套事务；任务初始化中第二步故障后验证整行回滚 |
| 多容器可能部分成功；原值快照未锁定 | 本次保存用一个外层事务；BLOB 原值在事务内 FOR UPDATE，缺行即失败 |
| 改等级忽略清处罚 SQL 的失败 | 传播 DELETE 错误并回滚等级和经验；触发器故障注入验证 |
| 邮件与附件删除不原子、可能误删其他角色附件 | 统一锁定、JOIN 清理、软删、提交；测试单条/批量失败与归属保护 |
| 克隆使用第一个槽作为模板，坏/满视图仍可能提交 | 按源角色查槽，复用还原的槽写入器；坏/缺/满视图拒绝提交 |
| 备份读取/写入失败被跳过，仍可能显示成功 | 检查全部 I/O，临时文件完成后原子替换；取消保留旧备份且清理临时文件 |
| 备份各表处于不同时刻 | 对目标基础表统一 READ 锁，覆盖 InnoDB 与 MyISAM；代价是阻塞写入 |
| BIT 被当数字、生成列被写入、零自增主键改变 | BIT 按二进制；显式可写列清单；NO_AUTO_VALUE_ON_ZERO；真实往返验证 |
| 角色备份缺结束标记检查 | 与全库备份共享完整性检查；截断文件被拒绝 |
| 还原失败污染会话；词法边界不完整 | 恢复外键、autocommit、sql_mode；处理未闭合引号/注释和 SQL 模式，拒绝会截断命令的 NUL 字节 |
| NO_BACKSLASH_ESCAPES 下文本转义错误 | 跟踪服务器状态并按模式转义；单引号、反斜杠实库写入验证 |
| 正好 0xFFFFFF 字节的 MySQL 包缺终止空包 | 修正发送分包；补接收序号、长度检查；实库边界查询验证 |
| UTF-8 过长编码、代理项和越界码点被接受；转换容量边界错误 | 严格验证码点，保护空/小输出缓冲区；内部自检覆盖 |
| 固定 Huffman 表首次初始化存在并发竞争 | 使用局部表；固定/动态已知压缩流、输出上限、预置字典拒绝自检 |
| NPK 同名项依赖不稳定 qsort 顺序 | 比较器显式按包加载序号、偏移排序，维持“后加载覆盖”规则 |
| 测试主动 skip 被计为 pass | 回归框架分别统计失败与跳过，防止验证范围被夸大 |
| 回归前置和清理不完整 | 扫描等待实际完成日志；在线夹具模拟近期登录；表单夹具同时还原金库时间；口令用例不输出真实口令；配置模糊测试在启动完成后才还原损坏配置 |
| 泡点缺少计费行时漏发、角色/账号统计混淆 | 先建账再带上界条件递增；按固定名单分别统计，失败计数为零；严格/非严格 SQL 模式实库验证 |
| 泡点包含已删除角色、指定不存在账号仍可发放 | 各入口排除删除角色和孤立账号，指定目标不存在时报错；合法无角色账号仍可收账号奖励 |
| 泡点重复查询在线集合，结算期间名单可能变化 | 事务内一次读取并锁定角色名单；账号去重；各奖励共用本次名单 |
| 泡点物品数量为零、时装宠物无附件行 | 复用正文/附件/邮寄统一路径；普通物品一封存数量，时装宠物逐件建归属行；全服物品明确拒绝 |
| 泡点后台读取可变配置、UI 与后台共享结果 | UI 启动前固定配置，线程结束后发布结果；日志使用本轮目标；奖励输入上限与 int 字段一致 |
| 邮件插入 ID 查询失败仍猜测最新记录；严格模式下时装缺必填 BLOB | 插入编号失败直接回滚，取消 MAX 回退；显式写入 jewel_socket，传播字符集设置错误 |

备份/角色备份共用序列化和失败清理，克隆/角色还原共用视图写入，
单条/批量邮件共用删除路径。简化重点是共享规则和明确失败处理。

测试库的 2 号角色在 charac_info 中存在，原始 charac_view 中缺少对应槽位。
克隆现在会明确拒绝这种源数据，避免猜测未知槽位字段。正常克隆的 GUI 用例在自己的
finally 还原范围内补充有效源槽位，缺槽位的回滚则由单独的无窗口用例验证。

## 真实游戏资源校准（第三批）

用户提供游戏目录 `D:\cache\game\opendnf-win-jbz69` 后，读取其中
`clients\jbz69\Script.pvf`（237,024,513 字节）和 `ImagePacks2`。
只读游戏资源；构建产物的 PVF/贴图配置已指向此目录，原配置副本保留在审查产物目录。

本批发现并修复了真实分类错误：原实现只依目录识别装备，漏掉 equipment.lst 中的
宠物、宠物装备，以及不在 avatar 目录中的时装。现在以 `[equipment type]` 校准分类：
`[creature]` 为宠物，三色 `[artifact ...]` 为宠物装备，含 avatar 的类型为时装，
没有该元数据时保留目录分类。`creature.lst` 是另一套定义编号，不能作为可发放物品 ID 兜底。
缓存版本升至 PVFC8，避免复用旧分类。

| 类别 | 旧分类条目数 | 修正后条目数 |
|---|---:|---:|
| 普通装备 | 49,975 | 30,438 |
| 时装 | 38,739 | 57,822 |
| 宠物物品 | 0 | 337 |
| 宠物装备 | 0 | 117 |

表中包含没有名称的定义；界面只显示有名称的物品，因此可见条目数更小。

宠物装备保留独立类型，并纳入装备浏览。

特殊道具发放同步修复：时装、宠物及宠物装备拒绝直接写入普通背包，
UI 与后台均校验，改用邮件。时装/宠物的数量 N 生成 N 个独立归属附件，

整个邮件队列在一个外层事务内执行，后续插入失败或取消会撤销前面已写入的正文与附件。
数量拆分使用 64 位中间值，避免加法溢出。

## 后续优化计划与验收标准

按以下顺序分批完成，每批保持可构建、可回归，避免一次重写扩大行为变化。

1. **业务语义校准**：PVF 的宠物/时装分类已修复，经验表已对照；继续验证游戏内
   等级经验、职业觉醒、任务标志、特殊附件领取；
   明确 `coin/pay_coin/cera/cera_point` 与界面名称。验收为 SQL 回读和游戏内实际效果一致，
   同时补正常、缺行、重复执行、失败回滚用例。
2. **补齐已识别的业务差口**：数值框清零交互、未知物品编号的发放策略；
   普通物品/时装/宠物的资源与数据库边界已增加本批实测，继续补游戏内领取验收。
   泡点缺行、删除筛选、名单冻结与到账统计已修复；当前在线规则保留在线账号下所有未删除角色，
   使用原有 login_status>=1 标志，是否改成仅当前游戏角色及如何识别过期在线位仍需业务确认。
   验收为一次结算的目标清单与实际收款账号/角色逐项一致，失败无部分到账。
3. **大表与备份工程**：MySQL 结果流式读取，导出内存不随最大表行数线性增加；
   对纯 InnoDB 提供一致性快照策略，混合引擎明确读锁窗口；记录每表行数、校验值及格式版本。
   用接近真实数据规模的备份还原测峰值内存、耗时、阻塞时间和逐表一致性。
4. **还原隔离与可恢复性**：明确哪些语句可回滚；对 DDL/MyISAM 设计独立恢复流程、
   检查表结构兼容性、外键重验及恢复中断后的重试。当前 CREATE TABLE IF NOT EXISTS
   不会将已有表自动迁移成备份结构，不应视为结构完全恢复。
5. **兼容性与连接层**：确定需要支持的 MySQL/MariaDB 版本、认证插件、TLS；
   对畸形/截断/乱序网络响应建立独立协议测试，检查重连、超时及资源释放。
   当前自带客户端主要面向 mysql_native_password，不具备通用驱动的全部能力。
6. **持续维护与简化**：为每个业务操作保留一个数据入口、一个事务边界和可定位的错误；
   按职责进一步拆分较大的 db_admin.c；逐步减少全局状态，保持 SQL 显式可读。
   仅在重复规则和测试证据充分时抽象，避免为缩短行数堆宏。
7. **长期运行与交付**：真实资源和游戏环境下补全部 manual 回归、长时间句柄/内存观察、
   写入中断和断网测试；将无数据库自检与有数据库集成测试分别纳入自动化。
   配置明文凭据与默认凭据的管理方式也需要单独改进。

## 实际边界

当前数据库样本只有两个角色，不能据此证明百万行扫描性能。
真实 PVF/ImagePacks2 已配置，资源解析和图标样本已对照；连续取码、游戏内显示、
附件领取与重新登录仍需可操作的游戏会话验证。
基础表备份不含视图、触发器、存储过程、计划事件或 MySQL 用户授权。
备份结束标记只能识别中断，不能证明内容未被修改。
自带 zlib 编码器采用 stored 块；格式兼容但压缩率不等同 Python zlib。
泡点按原有在线账号标志覆盖该账号的全部未删除角色；没有变更为“仅游戏中当前角色”。
本轮界面将 inventory.coin 统一标为复活币，与现有 GM 页一致；coin/pay_coin 的服务端
实际语义仍待游戏校准。泡点名单在内存固定，角色锁保留到结算完成，大规模名单的
内存、事务持续时间和对游戏写入的影响仍需实测。普通/时装/宠物的实库测试验证数据结构，
不代表样本物品已在真实客户端领取成功。
角色克隆和还原依赖服务端具体表结构；若业务表改为 MyISAM，不能依赖事务撤销其写入。
因此当前结论是“已验证路径的数据一致性和可维护性有明确改善”，并非全功能无差异或已达最优解。
