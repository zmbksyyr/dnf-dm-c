## 为什么不能直接改在线角色数据库

原游戏持有内存态并异步存档。Linux 原 ELF 已实际复现：内存复活币为 17，SQL 改为 40，
正常退出后被原存档覆盖回 17。点券另有缓存，改账单后等十秒 getter 仍可能是旧值。
这是两端共有的状态同步问题，不能按 Windows 字节不兼容处理。

正确路径分两种：

1. 已支持的在线能力：原游戏线程校验当前账号／角色／场景，调用原接口、通知客户端、
   请求原保存，再以相应 SQL 读回确认。数据库工作放异步 worker，回到游戏线程时重新查找对象。
2. 其他修改：等账号离线，在数据库事务内持有登录状态、归属和相关记录的锁至提交，
   写后核对；不能因为界面提前查过离线就直接执行 UPDATE。

GM 独立持有 `src/gm_bridge.lua`，从“关于 → 桥接”导出脚本、当前连接配置和简短说明。
按频道心跳、分项能力判断可用性；失效、缺表、旧模块或异频道时控件更新，后台也拒绝在线 SQL 回退。
恢复能力无需重连。Native 只随包打开独立 GM，不安装、配置或控制桥接；Robot 也不是前置条件。

证据：`cached-character-state/`、`gm-capabilities/`、`gm-online-{windows,linux}.private.json`、
`online-cera/`；实现／队列格式以当前 `src/gm_bridge.lua` 为准，不能另建重复接口绕开现有语义。

## 已确认在线操作的关键语义

| 操作 | 原游戏路径及必须保留的约束 | 证据目录 |
| --- | --- | --- |
| 金币 | `get_money/set_money`、原物品列表通知及原保存；先核对等级／PVF 金币上限和 int32 范围 | `online-money/` |
| 复活币 | `SetCoin/GetCoin`、`SendCoin/SaveMoneyCoin`；保存排队不等于落库 | `online-money/` |
| 疲劳 | `charac_stat.fatigue` 表示剩余，清零会耗尽；读原基础／额外上限，清 used，再核对保存 | `online-scalars/` |
| SP／TP | 四组通知为 16 位，限 0..65535；设置原技能脏标记并 `send_skill_info/UpdateData`，不能用普通属性保存代替 | `online-skills/` |
| QP | 原接口／通知为非负有符号 32 位，不能套 SP／TP 的 65535；保留重置次数、碎片及其他属性 | `online-qp/` |
| 点券／赠送点券 | SQL 锁内更新账单与刷新入队同事务；原游戏重新加载已提交账单并通知，不再次发放 | `online-cera/`、`gm-billing-edit/` |
| 装备栏／装备等级 | 原接口设置和通知，等级取当前 GM 配置；保留原支援兵等其他位 | `online-equipment/` |
| 负重上限 | 固定原属性块 +0x3a 的 int32，仅四字节应改变；走原通知／保存，避免覆盖整个结构 | `online-weight/` |
| 等级／经验 | 仅已支持的城镇角色，匹配 PVF 与游戏经验曲线；逐级原函数，核对等级、经验、SP／TP 与属性 | `online-level/` |
| PVP | 原战绩接口、通知 48 和保存；完整记录为 132 字节，保留其他字段，原段位范围 0..37 | `online-pvp/` |
| 任务设为可交付 | 先调用原条件检查，再临时 GM 标志调用 `quest_action(35)`，同步恢复标志，核对任务／槽位与存档 | `online-quest-api/` |

任务原函数存在先清进度、后查条件的顺序，因此必须在任何修改前做相同条件检查。
这不是直接发奖励；放弃、清空、初始化、清材料和模板导入仍为离线操作。
在线等级保存的经验实际位于 `charac_stat.exp`；`charac_info.exp` 可能保留旧值，不能单看后者判丢失。

### 保存失败和重试的语义

原 setter 成功不等于原保存完成。注入保存失败后，内存可能已变、SQL 未变，
应报告 `unknown`／`save_unconfirmed` 或对应已提交未确认状态，不能伪称回滚。
同目标重试需重新设置原脏标记并补存，不重复升级事件、奖励邮件或金币增量。
过期命令、旧 owner、错误当前角色、重复 token、丢失 worker 均有明确终态。
六并发增量的结果应全部累加；不能用读改写而未加锁的表面成功代替。

点券还须区分事务提交失败与提交后刷新回执丢失：后者必须说明余额已经写入，
不能重放发放动作。泡点异常会自动停用，控件、配置和实际调度状态要一致。

### 私有通知与公共广播必须分别处理

原 `SendPacket` 目标 0 为广播，1 为本人。负重／装备等私有属性需要本人通知，
等级公共信息仍按原协议广播。应以两个真实会话核对接收范围，不能只看目标角色数值变化。
证据：`gm-notify-recipients/final-summary.json`。

## 离线修改必须解决的竞态

统一流程是：固定入队时目标与载荷 → 开事务 → 锁账号登录记录或缺行范围 → 锁角色及业务记录 →
重新核对在线／退出中、归属、删除与字段条件 → 写入 → 完整回读 → 提交。
查询失败不作离线处理。检查须位于实际数据入口，不能只依靠 UI 置灰或轮询缓存。

| 场景 | 已复现问题／当前约束 | 证据 |
| --- | --- | --- |
| 六类容器批量保存 | 旧实现只比长度，同长度 zlib 内容被触发器改坏仍报成功；现在选中容器同事务逐字节回读 | `gm-containers/` |
| 宠物／时装修改 | 旧代码只按物品实例号更新，在线或错账号也可写；现在锁定登录、角色与物品至提交 | `gm-companions/` |
| 错误物品清理 | 重新验证完整 61 字节槽位／邮件附件快照，防止扫描后同一位置已换成另一物品 | `gm-cleanup/` |
| 改名／职业／副职业 | 执行时锁定账号与归属，等待锁后再核对；不能提前检查后无条件更新 | `gm-rename/`、`gm-profession/`、`online-expert/` |
| 克隆角色 | 固定源角色，列表及数量写后回读，关联表失败整笔回滚 | `gm-clone/` |
| 角色还原 | 拒绝取回已属于其他账号的编号，允许已删除／缺失角色按规则恢复；只执行受限备份 DML | `gm-restore/` |
| 账号金库金额 | uint32 范围，已有容量／物品不变；缺失或零容量从匹配 PVF 最小升级档读取 | `gm-account-money/` |
| 点券两个余额表 | 固定顺序加锁；“+1万”锁内累加；只改一项时保留另一项锁内新值 | `gm-billing-edit/` |

这些事务依赖参与表为 InnoDB；MyISAM 不能承诺回滚。已有／缺失登录行、等待期间上线或改归属、
严格／非严格 SQL、触发器改写和末尾失败都已有专项，不需要为相同路径重新从零造夹具。
后台不能读取后来变化的选中角色、容器或 PVF 来代替已确认的作业目标。

批量错误物品清理首次失败停止，已提交组数如实保留，不承诺跨组全部回滚。
无 PVF 时仅判断结构／孤儿记录，不判断物品 ID 不存在。
清邮件附件保留金币；“封装错误”“缺物品定义”“容器结构坏”分别定位，不自动清空整个背包。

## 字符编码：两个不同根因，不能混用修复

### 数据库名称有原服务的会话包装

固定原 ELF 使用 latin1 会话传 UTF-8 名称字节，utf8 列可能形成 Windows-1252 包装。
直接写看起来正常的普通 UTF-8 SQL 值，游戏读取反而可能出现问号。
历史“禁止二次转码”的笼统结论已被联调推翻。

已确认展示字段仅在完全可逆且结果为有效 UTF-8 时恢复，普通 UTF-8 原样保留。
名称／正文写入用局部 SQL 值转换，保留连接字符集与原始备份字节语义；不全库改编码。
搜索兼容两种存储，名字长度按原 ELF 字节容量限制，拒绝截断成功；charac_view 使用实际游戏字节。

### PVF 字符串表需要完整结构和整表码页

stringtable 是 count+1 个偏移对应 count 个字符串，二进制偏移区不能参与文本码页推断。
跨完整文本条目采样，统一选择 UTF-8／GBK／Big5；n_string 同样解析。
旧 PVFC8 已升级，后续语义变动也须升级对应缓存，不能永久复用旧输出。
stock PVF 物品 1“復活幣”与另一 PVF“复活币”保留各自用字，简繁不同不构成编码错误。

应同时核对原始数据库字节、GM Unicode、原游戏 getter、保存重登，不能只看 SQL 客户端或控制台。
证据：`encoding/`、`gm-rename/` 和 [编码修复记录](audit.md#原-elf-联调与中文修复2026-11-18)。
Robot 城镇字典解析和后来控制台显示误判另归 Robot `docs/knowledge.md`，不混成一个数据库编码问题。

## 邮件：发放、缓存删除与领取分开验证

邮件正文、postal 与时装／宠物关联记录须在同一事务中写入并最终回读，
收件人锁到提交，重新验证未删除及账号归属。宠物／时装每封对应一个实例，
不能接受会被忽略的多实例数量；需要多个时由发放页拆封。

在线发放使用原游戏邮箱加载机制；在线直接删除 SQL 后，已在内存中的附件仍可能领取。
因此删除／清理要求离线，不能把原邮箱查询成功当作缓存删除成功。
材料、时装、宠物附件已有原方法／协议领取对照，但每轮图形客户端范围须看对应记录。

Linux 原基线另出现未初始化邮箱游标（远大于数据库最大 postal 编号），发放后附件未载入。
独立诊断仅在确认空测试邮箱后调用原 `SetLoadState(true,0)`／`Init()` 才通过。
这轮不能标为未修改 Linux 基线通过，也不能在真实非空邮箱里无条件重置游标。
Native 的既有构造期标量初始化修复需按其源码与证据单独判断。

证据：`online-mail/`、`gm-mail-send/`。

## 备份、导入和验证本身的边界

- 角色级事务还原与整库导入不是同一操作。整库／通用 SQL 必须先停游戏服务；
  提前查在线标记不能阻止随后新登录，DDL 隐式提交也不能套用角色 DML 回滚承诺。
- 基础表备份不包含视图、触发器、存储过程、计划事件或用户授权；有结束标记不代表未被篡改。
- zlib 压缩字节不同可能只是编码器差异；应比较解压后槽位／字段和原游戏加载结果。
  反之，同长度压缩载荷也可能内容已坏，不能只检查长度。
- GM 异步作业、搜索和轮询要保留已选目标；状态栏容易被刷新覆盖，测试应读本次作业日志／终态。
- 主窗口关闭时模态循环曾吞掉退出消息；作业／弹窗退出也属于回归范围，不能只查写库结果。
- EXPLAIN 的账单文本主键查询曾从 ALL 变 PRIMARY／const，但千行样本不能代表百万行性能。
- 同机两套比较栈曾因 WSL 回环转发接错服务，或故障注入早于上一作业完成。
  应逐端运行，核对实际镜像／监听／数据库身份并等待作业终态，不放宽成功条件。
